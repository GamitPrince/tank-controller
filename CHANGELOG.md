All notable changes to this project are recorded here. Format follows Keep a Changelog; versions follow MAJOR.MINOR.PATCH (see the tag scheme in the GitHub Workflow Guide).

## [Unreleased]

### Added

- Repository scaffolding, CI, pull request policy and review rules.
- ADR-0003: firmware framework, language, structure and test tooling — Zephyr RTOS 4.5.0 pinned, C11, ztest and Twister on `native_sim` (#11).
- ADR-0004: communications architecture, data format and simulator — no separate gateway, own framed protocol over UART, CBOR records, MQTT over TLS, Python simulator (#12).
- ADR-0005: security design — per-device keys made on the board, own private CA, outbound-only TLS, signed boot (#13).
- ADR-0006: ESP32 communications firmware — ESP-IDF, C, Unity tests, secure boot and flash encryption on site units, A7672S over PPP (#14).
- ADR-0007: cloud architecture — managed AWS services, IoT Core as broker, Tiger Cloud for readings, with three gates before any account is opened or paid for (#15).
- ADR-0008: backend and dashboard — FastAPI backend, TypeScript and React dashboard, Amazon Cognito login, append-only audit trail, server-sent events (#16).
- ADR-0009: CI and deployment — Terraform or OpenTofu blueprints, test and live copies, OIDC login to AWS, free GitHub security set on every pull request (#17).
- `simulator/ci.sh` and `firmware/ci.sh`, the first component CI scripts, so the 80% line-coverage gate measures real code instead of passing on empty folders (#32). The simulator gets the `tanksim` Python package with pytest and ruff; the firmware gets ADR-0003's four layers (`hardware/`, `measurement/`, `record/`, `communications/`), a C11 measurement module with a ztest suite run by Twister on `native_sim`, `west.yml` pinning Zephyr 4.5.0, and gcovr filtered to `src/` so coverage counts the hardware layer too. Both report an out-of-range reading rather than clamping it. `gateway/` deliberately gets no script: it is obsolete under ADR-0004.

- The Phase 1 signal list and CBOR record schema, the first contents of `interfaces/` (#36). `signals-v1.yaml` defines the 23 plant signals from the EE's inventory of 20 Nov 2026 — two AD4111 4-20 mA channels, six 3-wire PT100s on one MAX31865, 15 of 16 optocoupler digital channels — plus three device-health signals, each with an id, name, unit, scale, update rate and read-only flag, and each digital channel with its contact sense and debounce. It replaces the register map (ADR-0004 decision 9). The two contact senses are deliberately not harmonised: normally closed on the safety-chain and alarm channels so a broken wire reads as alarm, normally open on equipment status so open means not running. Every signal is read-only, and volume, mass and level percent are absent because the cloud computes them (decision 10). `records.cddl` describes the CBOR scan record (decision 6); it versions independently of the list, every reading carries a quality flag and an age, and a faulted reading carries no value rather than a substituted one.

- The Phase 1 simulator, a standalone Python package that produces every signal in `interfaces/signals-v1.yaml` with no hardware (#38, ADR-0004 decision 13). One command, `python -m tanksim`, runs scans that each become a CBOR record validated against `interfaces/records.cddl` and framed with COBS, a sequence number and a CRC. The signal list and the schema are loaded at runtime, so no id, scale, channel number, debounce figure or quality code is written into Python, and a signal the plant model does not know is reported as unconfigured rather than invented. Fault injection covers a sensor fault (no value sent at all), an out-of-range value (sent as measured, not clamped) and a link drop, after which the buffered records are replayed carrying the timestamps of the scans that produced them; `--replay` does the same for a capture taken earlier. It carries the acceptance criterion P1-03 deferred to it: the CDDL schema validates a record the simulator produces, by interpreting the schema file itself rather than a copy of its rules. That check covers the subset of CDDL the schema uses and refuses to compile anything outside it; it is not a certified CDDL implementation, because `pycddl` could not be installed on the development machine.

- The first plant signal read: the high-high level trip and the low-low heater cut-off, read as status-only inputs (story S-022, P1-05, issue #45). `firmware/src/safety/` gains a debouncing reader that takes the contact sense, the 200 ms debounce and the 50 ms scan interval from `interfaces/signals-v1.yaml` at build time, so no id, channel number or debounce figure is written into C and adding a switch to the signal list needs no C change. Both channels are normally closed, so a de-energised switch or a broken wire reads as asserted and the debouncer does not smooth that away. A state is reported as live only while fresh samples keep confirming it: a channel that chatters, or that stops being sampled, keeps its last confirmed state but is no longer live. The module is input-only by construction and has no output, relay, coil or acknowledgement path. The ztest suite on `native_sim` covers both states, the transition, a channel stuck asserted, a channel that never settles, a stopped scan loop and a millisecond-counter wrap.

- The outage buffer: an append-only, delta-encoded flash log on the FRDM and a forwarder that sends it on oldest first, marking scans delivered only on a cloud acknowledgement (story S-039, P1-14, issue #81, ADR-0004 decisions 3 and 12). Every scan is logged first, so there is no buffer-start threshold. Entries carry a CRC-16 and are only written to erased flash, so a power cut never corrupts what was written before it. When the log is full the oldest sector is dropped and a gap recording the lost scans is forwarded. The ztest suites on `native_sim` include a 24-hour outage with a power cycle and an SNTP sync part-way, delivered afterwards with every original timestamp and nothing lost; that day used 2.03 MB of the 8 MB external flash, so the SD card fallback is not needed.

- A gap record in `interfaces/records.cddl`, so the cloud learns about scans the outage buffer had to drop instead of seeing a silent hole (story S-040, issue #83). It carries the number of scans lost and the boot id, seq, uptime and, when known, real time of the first and last of them. The firmware log now records that range when it drops a sector, carrying an older undelivered gap forward so neither its count nor the start of the hole is lost. The simulator's schema checker accepts the new record, and a record that matches no alternative now says why each one failed. The tech lead's follow-up decisions on S-039 are recorded: firmware-update slots stay in internal flash with a 984 KB image budget, a full scan every 60 scans, the delivered position saved every 60 acknowledgements, and batches of 16 to 32.

- Confirmed that the pilot FRDM-MCXN947 (board revision 170-90818 REV C) carries the standard Winbond W25Q64JV 8 MB NOR flash, so S-039's outage-buffer capacity calculation stands (story S-041, issue #85). Recorded in the S-039 and S-040 specs; the board photos stay in the private hardware location.

- Frames for the FRDM-to-ESP32 UART link, the first slice of P1-12 (story S-042, issue #87, ADR-0004 decisions 4 and 5). `firmware/src/communications/link_frame` COBS-encodes a version, type, sequence number, payload of up to 1024 bytes and CRC-16, ending each frame with a `0x00` delimiter, and decodes byte by byte, rejecting a bad frame with its reason and resynchronising at the next delimiter. Message types are RECORD, DELIVERED, LINK_STATUS and TIME; none carries a command. It uses only standard C so the ESP32 can share it. Delivery confirmation (retransmit, duplicates) is the next slice.

- Delivery confirmation on the FRDM-to-ESP32 UART link, the second slice of P1-12 (story S-043, issue #89, ADR-0004 decision 5). `link_sender` keeps one RECORD in flight, resends the same frame after 3000 ms without a matching DELIVERED, and gives up after 3 attempts so the outage buffer rewinds and resends later; both figures are provisional defaults. `link_receiver` passes each RECORD up once: a resend with the same sequence number, length and CRC-16 is dropped, and answered with DELIVERED again if it was already confirmed, so a lost acknowledgement does not stall the sender. Comparing the payload as well as the sequence number keeps a FRDM that reboots and restarts its numbering from being mistaken for a resend. Both use only standard C. Payloads are still opaque: the CBOR record encoder and the outage buffer's sender built on this are later stories.

- A CBOR encoder for scan and gap records on the FRDM, the third slice of P1-12 (story S-044, issue #91, ADR-0004 decision 6). `firmware/src/record/record_cbor` turns a flash log item into the exact `record` or `gap-record` of `interfaces/records.cddl` version 1, ready to be one RECORD frame's payload. The encoding is deterministic (RFC 8949 section 4.2.1), so the tests compare it byte for byte with records produced by Python `cbor2` and validated against the schema by the simulator. Input the schema would reject is refused rather than sent: no readings, an unknown quality code, a value on a fault or unconfigured reading, a bad device id, or a gap that counts nothing. `t` is written only when the time is known. The firmware limits the device id to 32 bytes so a worst-case scan (1004 bytes) fits the 1024-byte frame payload, which a build assertion checks. Digital values go out as the integers 0 and 1. No CBOR library is added.

- The flash log now goes to the ESP32 over the UART link, the fourth slice of P1-12 (story S-045, issue #92, ADR-0004 decisions 3, 5 and 8). `firmware/src/communications/uplink` is `log_forwarder`'s send function: each item is encoded as a CBOR record, sent as one RECORD, and waited on until the ESP32 confirms the cloud has it, with S-043's resends. `log_forwarder`'s send function now reports how many leading items were confirmed, so when the link gives up part way through a batch the confirmed items are acked in the flash log and only the rest are sent again; a gap record is no longer resent and counted twice for that reason. An item that cannot be encoded returns an error, is counted, and stays in the log. `link_sender` gains `wait_ms`, so the uplink never waits past a resend, and `abandon`, so a UART read error does not leave a RECORD stuck in flight. The firmware refuses to build if a CBOR record could outgrow one RECORD frame. The ztest suite on `native_sim` runs the real flash log, forwarder, uplink and S-043 receiver over a simulated link that drops RECORDs and DELIVEREDs, goes dead mid-batch, fails a read and sends noise, and checks that one item never takes longer than the attempts allow.

- The ESP32 firmware has a home, a top-level `esp32/` folder, and its first logic: the ESP32 end of the FRDM-to-ESP32 UART link, the fifth slice of P1-12 (story S-047, issue #97, ADR-0004 decisions 3 to 5, ADR-0006). `esp32/components/link_endpoint` takes UART bytes, passes each new record up once, and writes DELIVERED back to the FRDM only when the upper layer reports the cloud has it; a record resent after a lost DELIVERED is confirmed again and not passed up twice. It is standard C over the shared link library, tested with Unity on the host as ADR-0006 decides, including an end-to-end test against the FRDM's sender with a lost RECORD and a lost DELIVERED. `esp32/ci.sh` fetches Unity v2.6.1, checks formatting against the firmware's `.clang-format` and writes `coverage.xml`; a new `esp32` CI job runs it and `ci-gate` requires it. ESP-IDF itself, the UART driver, Wi-Fi, the modem, TLS and MQTT come in later stories.

- The FRDM's UART to the ESP32 is driven from Zephyr, the sixth slice of P1-12 (story S-048, issue #99, ADR-0004 decision 4). `firmware/src/hardware/esp32_uart` gives the uplink its read, write and clock functions on a real Zephyr UART: received bytes are moved by the UART interrupt into a ring buffer and decoded into frames, and frames are written byte by byte. A full ring drops and counts bytes, and S-043's resend recovers the record. Boot code finds the UART through the devicetree chosen node `tank,esp32-uart`; the board's instance, pins and baud rate (115200 8N1 for now) wait on the EE's pin mapping. The ztest suite runs on Zephyr's emulated UART, including an end-to-end run from the flash log through the forwarder, uplink and driver to an emulated ESP32 that loses a DELIVERED.
- The log forwarder runs in its own thread, the seventh slice of P1-12 (story S-049, issue #101). `firmware/src/communications/uplink_service` polls the forwarder: it drains a backlog batch after batch, waits `idle_ms` (1000 by default) when caught up and `retry_ms` (5000) after a failed send, and stops promptly on request. The flash log now holds a mutex for each append, read, ack and rewind, so a scan thread can append while the service forwards; a slow link never blocks an append. A batch dropped by a full ring while in flight can make a gap overstate the loss, never hide it.

### Changed

- Review rules now require one approval from a collaborator other than the author, replacing the "all three developers" rule for `interfaces/`. CODEOWNERS, the `interfaces-review` check and the pull request template were updated, and the `INTERFACE_REVIEWERS` variable set to `GamitPrince,prinz-assists` (#19). Verified end to end in #23: `interfaces-review` reports success on one non-author approval.
- `AGENTS.md` aligned with the rule above; it had asserted the old rule in three places while stating the new one in section 3 (#22).
- The electrical engineer (`@gamitriyan-del`) added as a code owner of `interfaces/`, `.github/` and `scripts/`, so that approvals on those paths do not depend on a single collaborator. Safety paths are unchanged and still require the EE.

- Simulator pins raised to clear four Dependabot alerts (S-026): `cbor2` 5.6.5 to 5.9.0, which closes two high and one moderate decoder advisory, and `pytest` 8.3.4 to 9.0.3 with `pytest-cov` 7.1.0, which pytest 9 requires. Real exposure in the simulator was low — its one `cbor2.loads` call decodes payloads it produced itself — but the cloud backend of P1-17 will decode real device CBOR off the broker, which is untrusted input, so it starts from a patched decoder. `pyproject.toml` needed no change: `cbor2>=5.6,<6` already admits 5.9.0.
- The tech lead's decision review of 26 Nov 2026 recorded in `AGENTS.md` and the story pages (S-053): P1-11 (Modbus) and P1-13 (OPC UA) void; density-based mass removed from Phase 1 and S-037 closed; GamitPrince owns the dashboard and prinz-assists QA; no ruleset bypass list; the backend, Terraform, migration, registry, MQTT topic and batching choices; one consolidated record per second; the status of ADR-0007's three cloud gates.
- `gateway/` removed with its CI job, the `gateway` title scope in `pr-policy`, the template options and the docs that still offered it (S-055; ADR-0004 decision 1, tech lead decision of 26 Nov 2026).
- The FRDM-to-ESP32 link library (`link_frame`, `link_sender`, `link_receiver`) moved unchanged from `firmware/src/communications/` to `shared/link-protocol/`, which both boards build (S-056, ADR-0003 amendment 1). The firmware job still formats, checks, tests and measures it; CI now runs the `firmware` and `esp32` jobs when it changes.
- cppcheck now runs in CI and blocks the firmware job on errors, warnings and portability findings; style and performance findings are shown but do not block. The firmware job caches the west-fetched Zephyr tree, keyed on `firmware/west.yml` and `firmware/requirements-dev.txt` with no fallback key (S-057, ADR-0003 amendments 2 and 3).

- The scan builder (S-058): one call turns the current state of the 23 Phase 1 inputs into the record the flash log stores, with loop currents in microamps, temperatures in centi-degrees, contacts as 1 or 0, each reading's quality and age, and the boot-time header. Faults and never-read inputs carry no value, and a contact whose state has not yet survived its debounce is a fault. Read-only: nothing in `firmware/src/safety/` changes.

- The scan service (S-059): a thread takes a scan every second with the S-058 builder and appends it to the flash log, network or not. It runs above the uplink service so forwarding never delays a record, keeps to a fixed grid that does not drift, skips and counts grid points an overrun missed instead of bursting, and holds an optional lock shared with whoever updates the inputs. seq advances per scan built, so a scan the flash failed to store shows as a gap.

- The firmware application (S-060): `firmware/app/` boots with a fresh random boot id, mounts the flash log on the devicetree's `tank,log-partition`, sets up all 23 Phase 1 inputs from the signal-list tables and starts the one-second scan thread, network or not. Built for native_sim in CI until the board overlay exists. Until the pins are read, every reading goes out without a value (unconfigured or fault). The P1-09 alarm table's generated header is now `tank_alarm_signals.h`, with its own include guard, so both safety tables build in one application.

- The application forwards its flash log to the ESP32 (S-061): after scanning starts, it brings up the ESP32 UART from the devicetree's `tank,esp32-uart`, the uplink, the log forwarder (batch 16) and the uplink service (idle 1 s, retry 5 s). Scanning never waits for the link. Records carry the device ID, the MCU's factory unique ID read with hwinfo and written as lowercase hex (tech lead, 26 Nov 2026); without one the device still logs, just without forwarding.

- The record schema gains the batch message (S-062): `batch = [1*5 message]`, one to five complete records, oldest first, which the FRDM packs into one link frame and the ESP32 publishes as one MQTT message on `tank/{device_id}/records`. A single record stays valid on its own, and `v` stays 1.

- The FRDM packs up to five records into one link frame (S-063): the uplink sends the S-062 batch, oldest first, and one DELIVERED confirms the frame; the link payload limit rises from 1,024 to 5,120 bytes to fit five worst-case records. The uplink service treats a part batch as caught up, and the application polls every 5 s, so steady state is one frame of five records every 5 s and a backlog drains frame after frame.

- The ESP32 publisher (S-064): each RECORD the FRDM sends, one batch of up to five records, is published unchanged at QoS 1 as one MQTT message on `tank/{device_id}/records`, and DELIVERED goes back to the FRDM only when that message's PUBACK arrives. A failed publish or a stale PUBACK confirms nothing, so the FRDM keeps the records. Host-tested logic; the ESP-IDF MQTT glue comes with the first ESP-IDF build.

- A change goes out at once (S-065, NFR-01): when a logged scan differs from the one before in any contact's value or any reading's quality, the scan service kicks the uplink service, which polls straight away instead of finishing its 5 s wait. Analogue noise does not count, so steady readings still travel five to a frame.

- The backend skeleton (S-066, ADR-0008): the root `backend/` folder holds a FastAPI app whose one endpoint, `GET /health`, reports the status and the app version, tested with pytest and held to the 80% gate by `backend/ci.sh` and a new `backend` CI job. It runs locally only; no database, ingest or cloud account yet.
- The backend decodes the CBOR batch message (S-067, ADR-0004 decision 6): `tankapi.records.decode_message` turns one MQTT message into typed scan and gap records, oldest first, with every quality flag and age kept and no faulted value filled in. A malformed message is refused with the failing record and field named, and the whole message is checked before anything is returned. A test reads `interfaces/records.cddl` so the decoder's version and quality codes cannot drift from it. Nothing is stored yet.
- The backend database schema (S-068, ADR-0007, ADR-0008): SQLAlchemy models and the first Alembic migration under `backend/migrations/` create `scan_records` and `readings`, holding every field the decoder gives without loss. Check constraints keep a faulted or unconfigured reading without a value and refuse a substitute, and `(device_id, boot_id, sequence)` is unique for the later de-duplication story. Tested on SQLite, with the Postgres DDL rendered offline; the gap-record table, TimescaleDB and writing records come later.
- The gap-record table (S-069, S-040): Alembic revision 0002 adds `gap_records`, holding `lost` and both lost-scan marks of every decoded gap record, with check constraints matching the decoder, so the holes in a device's data can be stored alongside its scans. Nothing may interpolate across a gap; writing and de-duplicating gaps come later.
- Storing decoded records (S-070, ADR-0004 decisions 7 and 8): `tankapi.store.store_message` writes the records of one MQTT message into the backend database in one transaction, all or none. MQTT QoS 1 delivers at least once and a backlog is replayed after an outage, so a scan whose device, boot ID and sequence are already stored, or a gap identical in every field to a stored one, is skipped and counted, never overwritten. The device's own timestamps are kept, never the arrival time. No migration; ingest comes later.
- Ingesting one MQTT message (S-071, ADR-0004 decision 7, ADR-0005): `tankapi.ingest.ingest_message` takes a message's topic and payload, checks the topic is exactly `tank/{device_id}/records` with a schema-valid device ID, decodes the batch, and stores it with `store_message`, returning how many records were stored and skipped. A wrong topic, a payload that does not decode, or any record whose `dev` is not the topic's device refuses the whole message: nothing is written, and the refusal is logged with the device ID, reason and payload size, never the payload. A database failure is raised so the message can be delivered again. Nothing is published to any device; the queue consumer and a dead-letter store are later stories.
- Querying stored readings (S-072, ADR-0008 decision 7): `GET /v1/devices/{device_id}/readings?signal=<id>&from=<t>&to=<t>`, the first versioned REST endpoint, returns one signal's stored readings with scan times in `[from, to)` (Unix seconds, at most one hour and 3600 points), oldest first. Every point carries its quality and age; a faulted or unconfigured reading comes back with no value, and values stay scaled integers with the signal-list version, for the client to scale. Gaps that overlap the range are returned as gaps, nothing is interpolated, and scans with no wall-clock time are counted rather than given one. Read-only (any write method gives 405) and unauthenticated: local only until the login story lands.
- The ownership tables (S-073, ADR-0005 decision 2, ADR-0007 decision 2, ADR-0008 decision 3): Alembic revision 0003 adds `customers`, `plants`, `tanks`, `devices` and `device_assignments`, so the backend knows which customer, plant and tank each device is on. Assignments keep their history, at most one open per device, so a moved device's old readings still belong to the tank they were taken on. The record tables, ingest and the readings endpoint are unchanged; nothing reads or writes the new tables yet.
- Resolving a device to its owner (S-074, ADR-0007 decision 2, ADR-0008 decision 3): `tankapi.ownership.owner_now` and `owner_at` say which customer, plant and tank a device is on, now or at a given Unix second, or that it is unclaimed at that time or unknown. An assignment's start is included and its end is not. Overlapping assignments raise instead of picking a customer, and a scan with no known time cannot be placed. Read-only: no endpoint, no migration, and nothing calls it yet; the login story will.
- Checking the caller's token (S-075, ADR-0008 decisions 2 and 3, ADR-0005 rule 9): every `/v1` request now needs an Amazon Cognito access token in `Authorization: Bearer`. `tankapi.auth.require_caller` accepts only RS256, with a `kid` from the configured JWKS, the configured issuer and app client (`client_id`), `token_use` `access`, a subject, and `exp` and `nbf` within 30 s of the server's clock; `none`, HS256 and symmetric keys are refused. Any other token, or none, gets 401 with `WWW-Authenticate: Bearer` and a body that does not say why. The issuer, the app client and a local JWKS file or the pool's HTTPS JWKS URL are environment settings; without them every `/v1` request gets 503, while `/health` stays open. The tests sign their tokens with RSA keys generated at run time and make no network call. Adds PyJWT 2.15.1 with cryptography 50.0.2. The caller's role and customer come in S-076, and until per-customer scoping lands any valid token reads any device, so the API stays local only.
- Reading the caller's role and customer (S-076, ADR-0008 decision 3): after the token check, `require_caller` returns the caller's role, the one of `operator`, `maintenance`, `admin` or `service` named in `cognito:groups` (other group names are ignored), and their customer, `custom:customer_id` as positive decimal digits. No role, two roles, or a missing or malformed customer gets 403 with a fixed body; the reason is logged, the token never is. A service caller (our staff) carries no customer, and any customer value on its token is ignored. All four roles may read the readings endpoint. Not yet done: per-customer scoping, per-role permissions and the audit trail, so service access is not audited and the API stays local only.
- When a device was on a customer's tanks (S-077, groundwork for P1-20): `tankapi.ownership.customer_windows` returns, for one customer and a time range, the stretches in which the device was on that customer's tanks, by the same rules as `owner_at` and checked against it second by second. A move between the customer's own tanks keeps one stretch; a move to another customer or a release ends it. A device whose assignments overlap anywhere is refused, not guessed. Read-only; nothing calls it yet (the readings scoping is S-078).
- Readings limited to the caller's customer (S-078, P1-20, ADR-0007 decision 2, ADR-0008 decision 3): an operator, maintenance or admin caller of `GET /v1/devices/{device_id}/readings` sees a scan only if the device was on one of their customer's tanks at its time, so readings from before a claim or after a release are shown to nobody. They see no untimed scan (`untimed` is null) and only gaps lying wholly in their time. Another customer's device, or a time outside theirs, gets the same 404 as an unknown device, so IDs cannot be probed. Overlapping assignments give a fixed 500, logged without the token. Service sees every device. Not yet done: the audit trail, so service access is not audited and the API stays local only.
- Append-only audit table (S-079, ADR-0008 decision 4): migration 0004 adds `audit_entries`, with when, the caller's `sub` and role, method, route template, device ID, the selecting query parameters and the response status, and no column for a token, a header or a reading. Database triggers refuse UPDATE and DELETE (SQLite tested; the Postgres form, which also refuses TRUNCATE, is untested until the TimescaleDB container story). Nothing writes it yet: recording service-staff requests is S-080.
- Service-staff access audited (S-080, P1-20, ADR-0008 decision 3): every `/v1` request by a service caller writes one row to the append-only `audit_entries` table (S-079), refused requests included: when, the caller's `sub` and role, method, route template, device ID, the `signal`, `from` and `to` parameters as sent (each cut to 64 characters), and the response status. The token, headers, other parameters and readings are never recorded. If the entry cannot be written the request gets 503. Customer callers are not recorded. Not yet done: the daily S3 Object Lock copy, the Cognito user pool and ADR-0007's gates, so the API still stays local only.
- Level % and volume calculation in the backend (S-082, P1-04, ADR-0004 decision 10): `tankapi.level.compute_level` turns the radar loop current (signal 1001) into a level height, level % and volume from a tank's transducer range and strapping table by linear interpolation, never extrapolating; a faulted, stale or out-of-range input gives an explicit status and no figures. Each result carries the table version and the calculation version (ADR-0007 decision 9). No mass. Not stored or called yet; tested on a made-up table only.
- Stale-reading rule in the backend (S-083, P1-19, ADR-0008 decision 6, ADR-0004 decision 11): `tankapi.liveness` says whether a stored reading is `live`, `stale` or `time-unknown` against the server clock, so stale data is never shown as live (AGENTS.md section 7). A scan with no known time, or one ahead of the server clock, is never live; the device's `stale` quality, an `age` over two update periods, or no newer scan within the signal's update period plus 14 s makes a reading stale. Quality is never changed. Thresholds are environment settings, update periods the signal list's. Not served by the API yet (S-084).
- Latest values with a stale flag (S-084, P1-19, ADR-0008 decision 6): `GET /v1/devices/{device_id}/latest` returns each signal's newest reading with its quality, age and S-083's `liveness`, plus whether the device itself is live, stale or `time-unknown` (clock not yet set). A value that is no longer current is returned flagged, never as live. A customer's caller sees a device only while it is on one of their tanks, and no scan from before the claim (S-078); service requests are audited (S-080). GET only.
- Each tank's level configuration stored with its history (S-085, P1-04, ADR-0004 decision 10, ADR-0007 decision 9): migration 0005 adds `level_configurations` (table version, the calculation version it is used with, transducer range, full height, valid from and to) and `strapping_points`. The database refuses a point that does not rise in both height and volume over the one before it, a gap in the points, a negative, NaN or infinite number, and a second open configuration for a tank. Nothing reads or writes them outside the tests yet; every table in them is made up.
- Level % and volume served from stored radar readings (S-086, P1-04, ADR-0004 decision 10): `GET /v1/devices/{device_id}/latest` gains `level`, computed on read with `compute_level` from the newest radar reading shown and the configuration of the tank the device was on at that reading's time (`tankapi.level_config.level_config_at`, `tankapi.tank_level`). It carries the reading's quality, age and liveness, the table and calculation versions, and figures only when its status is `ok`; otherwise `no_reading`, `unconfigured`, `stale`, `time_unknown`, `fault` or `out_of_range` says why. Nothing is stored, substituted or extrapolated; overlapping or broken configurations give 500.
- Advisory alarm thresholds stored per tank with their history (S-087, P1-18): migration 0006 adds `alarm_thresholds`, one high or low limit of class critical, warning or advisory with a deadband, on one of the eight analogue signals (in its transmitted unit) or on level % (in hundredths of a percent), dated from and to so a change keeps the old limit. The database refuses a threshold on a device contact or health signal, a level % limit outside 0 to 100 %, a negative deadband and a second open threshold of the same kind. These alarms are reports for people only, never sent to a device; judging values, alarm events, the read endpoint and acknowledgement are later stories.
- A value judged against an advisory alarm threshold (S-088, P1-18): `tankapi.alarm_rules.evaluate` returns normal, high, low or `cannot_evaluate` with the reason, for one stored analogue reading or S-086 level % and one S-087 threshold. A high threshold is reached at its limit and, once raised, stays raised until the value falls below the limit less the deadband; a low one is the mirror image. A fault, unconfigured, stale, untimed or missing value never raises or clears an alarm and is never reported as normal; an out-of-range reading is judged as measured. A test checks that no backend module imports an MQTT or AWS client.
- An append-only history of advisory alarms (S-089, P1-18): migration 0007 adds `alarm_events`, one row per change of an alarm's state (raised high or low, cleared, or `cannot_evaluate` with the reason), naming the threshold row in force at the scan's time with a copy of its limit and deadband, the value judged, the reading's quality and the scan with its time, never the time of arrival. Triggers refuse UPDATE and DELETE, as for the audit trail; the Postgres form is rendered but not yet run on a server. `tankapi.thresholds.thresholds_at` returns a tank's thresholds in force at a time. Writing the rows from stored scans is S-090.
